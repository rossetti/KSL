# Guide: fitting a mixture of distributions

**Packages:** `ksl.utilities.distributions.fitting.mixture` and its `partition`, `refine`,
`scoring` and `search` subpackages, `ksl.utilities.distributions.fitting.diagnostics`, and the
mixture report extensions in `ksl.utilities.io.report.extensions`.

**New in R1.7.**

> **Status: experimental.** These packages are released as experimental. Their public API may
> change in future releases without notice. Pin your KSL version if you build against them for
> production use.

Runnable examples live in
`KSLExamples/src/main/kotlin/ksl/examples/general/utilities/fitting/mixture/`, eight of them, meant
to be read in order. For the step-by-step walkthrough see
[`ksl-mixture-tutorial`](ksl-mixture-tutorial.md); this guide is the reference.

---

## 1. What this package is for

`PDFModeler` fits a catalog of named distributions to your data and ranks them. That is the right
tool when one shape will do. When it will not, the ranking is still produced — a score compares the
candidates you offered, and says nothing about whether any of them belongs. You get a
recommendation that is the best of a bad set, with nothing in the output marking it as such.

Data generated by more than one mechanism is the usual reason. Service times at a desk serving
three kinds of visitor, repair times for two failure modes, durations that depend on a hidden
class. The measured quantity is one variable; the process behind it is not one process.

A mixture models that directly: several component distributions, each with a mixing weight. This
package fits one to univariate data by partitioning the sorted sample into contiguous groups,
fitting a component to each group, assembling the best combination, and scoring it.

**When not to use it.** A mixture always fits better than a single distribution, because it has
more parameters. That is not evidence for it. Before reaching for one, ask whether you can name the
mechanism — "these are three kinds of visitor" — because without a mechanism the components will
fit but will not correspond to anything, and the number of them will not be recoverable. If all you
need is a density that behaves like the data, a single distribution is the more defensible model.

---

## 2. The mental model

Five pieces, assembled in order. `MixtureModeler` supplies a default for each, and each is an
interface you can replace:

1. **Partition generator** (`PartitionGeneratorIfc`) — cuts the sorted data into k contiguous
   groups. Jenks natural breaks by default; quantile and histogram-valley are also provided.
2. **Refiner** (`PartitionRefinerIfc`) — improves the cuts. Break-shift local search by default.
3. **Component fitter** (`ComponentFitterIfc`) — fits candidate families to a group. Delegates to
   `PDFModeler` by default.
4. **Family selector** (`FamilySelectorIfc`) — chooses one family per group from those that fitted.
5. **Criterion** (`MixtureCriterionIfc`) — ranks assembled mixtures. BIC by default.

The whole pipeline runs once per component count in the range you ask for, and the results object
holds all of them, not just the winner.

**Two consequences worth internalising.** The partition is *contiguous*: components are separated
by cut points along the number line, not assigned observation by observation. That is what makes
the search tractable and also what makes heavily overlapping components hard to recover. And the
fitted result is an ordinary `ContinuousDistributionIfc`, so everything downstream — plots,
goodness-of-fit tests, random variate generation — works unchanged.

## 3. Quick start

```kotlin
val data = receptionDeskData()
val modeler = MixtureModeler(data)
val results = modeler.fit(numComponentsRange = 1..6)
println(results)
```

The fit is a distribution:

```kotlin
val results = MixtureModeler(receptionDeskData()).fit(numComponentsRange = 1..6)
val fitted = results.best!!.distribution
println(fitted.mean())
println(fitted.invCDF(0.5))
val generated = fitted.randomVariable(streamNumber = 99).sample(5)
```

And one line produces the standard report, plots included:

```kotlin
val results = MixtureModeler(receptionDeskData()).fit(numComponentsRange = 1..6)
results.showHTMLInBrowser(heldOut = receptionDeskHoldOut())
```

## 4. How do I...?

### ...see how every criterion scored, not just the winner?

```kotlin
val results = MixtureModeler(receptionDeskData()).fit(numComponentsRange = 1..6)
println(results.criterionSummary())
```

Report them side by side rather than combining them. They are all penalised likelihoods differing
in how much they charge per parameter, and averaging them manufactures an agreement the evidence
does not support.

### ...find out whether the component count is believable?

Refit on resampled data. If one count wins nearly every resample, the data determine it; if two are
close, the recommendation is nearly a coin toss.

```kotlin
val data = receptionDeskData()
val boot = MixtureBootstrap.componentCountFrequency(
    data,
    numBootstrapSamples = 100,
    numComponentsRange = 1..6
)
println(boot)
```

### ...build the pipeline myself?

```kotlin
val sorted = receptionDeskData().sortedArray()
val k = 3
val certificate = AdmissibilityCertificate(sorted)
val fitter = ComponentFitCache(PDFComponentFitter(PDFModeler.allEstimators, false))
val criterion = MixtureBICCriterion()
val selector = SeparableCMLSelector()
val initial = JenksPartitionGenerator(sorted, k).generate(sorted, k, certificate) ?: return
```

**Wrap your fitter in `ComponentFitCache`.** Fitting a group runs the whole estimator catalog over
it, which dominates the cost of everything else, and refinement moves one cut at a time so
consecutive partitions share most of their groups. `MixtureModeler` does this for you; when you
assemble the pipeline yourself, nothing will.

### ...check the fit against a truth I know?

Available when the data was simulated, which for a simulation library is often:

```kotlin
val results = MixtureModeler(receptionDeskData()).fit(numComponentsRange = 1..6)
val mixture = results.best!!.candidate
val recovery = RecoveryMeasures.compare(
    receptionDeskWeights, receptionDeskComponents, receptionDeskFamilies,
    mixture.weights, mixture.distributions, mixture.components.map { it.rvType }
)
println(recovery.hellinger)
println(recovery.numComponentsCorrect)
```

`RecoveryMeasures` compares densities rather than family labels, because those labels are not
always identifiable — an exponential is a gamma of shape one — and a comparison keyed on the label
reports failures that are not failures.

### ...score the fit on data it never saw?

```kotlin
val results = MixtureModeler(receptionDeskData()).fit(numComponentsRange = 1..6)
val mixture = results.best!!.candidate
val evaluation = mixture.logLikelihood(receptionDeskHoldOut())
if (evaluation.isUsable) {
    println(evaluation.value / receptionDeskHoldOut().size)
}
```

Check `isUsable` rather than skipping it. If any held-out observation lands where the fitted
mixture has zero density, the log-likelihood is negative infinity and the average is meaningless.

### ...produce a report with everything in it?

```kotlin
val data = receptionDeskData()
val modeler = MixtureModeler(data)
val results = modeler.fit(numComponentsRange = 1..6)
val report = results.showHTMLInBrowser(
    heldOut = receptionDeskHoldOut(),
    title = "Reception desk service times",
    description = modeler.describe(),
    stability = modeler.partitionStability(results),
    adequacy = modeler.assessFitAdequacy(results),
    bootstrap = MixtureBootstrap.componentCountFrequency(data, numBootstrapSamples = 100),
    variableName = "service time (minutes)"
)
println(report.absolutePath)
```

Each optional argument adds a section; omitting one omits that section. `asHTML` and `asMarkdown`
return the text instead of opening it, and `toReport` takes a trailing block for sections of your
own.

### ...get the results as data rather than prose?

```kotlin
val results = MixtureModeler(receptionDeskData()).fit(numComponentsRange = 1..6)
println(results.componentsAsDataFrame())
println(results.criterionProfileAsDataFrame())
```

## 5. The key types at a glance

| Type | What it is |
|---|---|
| `MixtureModeler` | The entry point. Holds the data, runs the pipeline, produces the analyses |
| `MixtureModelingResults` | Everything one run produced, across all component counts |
| `RankedMixture` | One evaluated candidate: the mixture and its criterion value |
| `MixtureCandidate` | One assembled mixture — partition, components, weights |
| `PartitionGeneratorIfc` | Cuts sorted data into k groups; Jenks, quantile, histogram-valley |
| `PartitionRefinerIfc` | Improves the cuts; break-shift or classification EM |
| `ComponentFitterIfc` | Fits families to one group; `PDFComponentFitter`, `WindowedComponentFitter` |
| `ComponentFitCache` | A memoizing decorator for any fitter. Use it |
| `FamilySelectorIfc` | Picks one family per group; separable or exhaustive |
| `MixtureCriterionIfc` | Ranks mixtures; BIC, AIC, Hannan-Quinn, ICL-BIC, EBIC, held-out |
| `MixtureBootstrap` | Refits on resampled data to test how firm the component count is |
| `RecoveryMeasures` | Compares a fit against a known truth |
| `ModalityAnalyzer` | How many modes the data appears to have, before anything is fitted |
| `AdmissibilityCertificate` | The structural facts of a sample that decide which partitions exist |

## 6. Gotchas and best practices

**A mixture always fits better.** More parameters, better likelihood. The criterion's penalty is
what stands between you and fitting one component per observation, so read the criterion, not the
likelihood.

**Check whether the best k sits at the top of your range.** If it does, the criterion did not
choose — it ran out of candidates, and would have kept going. That looks identical to a genuine
choice if you print only the winner. Print the profile.

**The component count is the least reliable output.** On data where the truth is known, the best
criteria recover it well under half the time. The fitted *density* is usually good; the
decomposition usually is not. Use the mixture to generate values, and be cautious about
interpreting its parts.

**Goodness-of-fit tests are weak evidence here.** Both the mixture and the single distribution were
chosen by looking at the same data they are then tested against. Read the tests as a comparison
between the two, and treat held-out coverage as the honest check.

**Modes bound the component count from below, only.** A two-component mixture can be unimodal, so
one hump does not mean one component. `ModalityAnalyzer` answers the question it is asked, which is
about the density's shape rather than about the number of mechanisms.

**Cache your fitter.** See §4. The default pipeline does it; a hand-assembled one does not.
